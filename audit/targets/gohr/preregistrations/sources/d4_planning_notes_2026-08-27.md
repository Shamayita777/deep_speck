# Dataset Integrity — Redesign From First Principles

No code. This is the design pass.

## The conceptual tool I'll use throughout

Before touching individual audits, one distinction has to be load-bearing across everything below, because it's where the current design mostly goes wrong: **exhaustive census ≠ statistical inference ≠ analytical guarantee**, and **instance audit ≠ procedure audit**.

- **Detecting a problem**: a test ran and flagged something specific.
- **Finding no evidence of a problem**: a test ran, found nothing, but its coverage is bounded — this is absence of evidence, not evidence of absence, and the certificate must state the bound.
- **Statistically establishing a property**: a formal test with a stated null, an effect size, and a decision rule computed from a sample — inherently probabilistic, inherently bounded by sample size.
- **Proving a property**: only achievable for finite, fully-enumerable checks (an exhaustive hash census over the *entire* dataset) or for analytically-derived guarantees (a birthday-bound argument over a known keyspace and entropy source). Neither requires a p-value, and neither should be reported using the same decision vocabulary as a statistical test — conflating "p=0.31, inconclusive" with "0 found in a complete census" under one `SUPPORTED`/`NOT_SUPPORTED` label is itself a scientific-honesty failure.
- **Auditing a dataset instance**: verifying a property of the *specific bytes* used to train/evaluate a specific checkpoint.
- **Auditing a dataset-generation procedure**: verifying a property of the *process* that produces datasets like this one — doesn't require the historical instance, but the claim only transfers to "a typical draw from this procedure," not to any specific past run.

This last split is the actual root of D1's stated weakness, and it recurs in B, C, and G below. I'll flag every audit's tier explicitly rather than letting it default to whichever one happens to be easiest.

## A. Exact Duplicates — redesigned

**1. Threat**: identical samples appear more than once within a partition (inflates effective sample count, biases variance estimates) or across partitions (direct train/test leakage).
**2. Claim**: two-tiered — *instance*: "the dataset actually used for this training run contains zero byte-identical duplicates, within and across partitions." *Procedure*: "datasets generated by this procedure at this sample count have negligible duplicate probability."
**3–6. H0/H1/Treatment/Control**: not a treatment/control design — this is diagnostic/exhaustive census, not an experiment. H0 for the instance tier is simply `duplicate_count = 0`, established deductively over the checked population, not inferred.
**7. Held constant**: the representation hashed must be the *exact post-preprocessing, model-consumed* encoding — hashing pre-transform data would miss samples that differ before transformation but collapse to the same input the model actually sees.
**8. DV**: duplicate count, duplicate groups, max multiplicity, per-partition and cross-partition.
**9–12. Statistical unit / method / effect size / CI**: none, for an exhaustive census — there's no sampling variance to speak of. Where a scan must be coverage-limited, it converts into a genuinely inferential claim and needs a coverage bound (see B).
**13. Decision rule**: `duplicate_count == 0` → pass, for the checked population, full stop.
**14. Establishes**: for an exhaustive hash over the *actual* instance, this is as close to proof as computation allows (modulo negligible SHA-256 collision probability).
**15. Does NOT establish**: near-duplicates; and — this is the part currently missing — it does **not** establish anything about any *other* dataset instance generated by the same unseedable procedure, unless the procedure-tier claim is separately and explicitly justified.
**16. Type**: diagnostic-exhaustive — a new category worth naming explicitly, since it's neither purely descriptive nor classically inferential.
**17. Certificate**: yes — this is a straightforward, low-cost fix.
**18. Provenance**: a single content-hash of the *entire* persisted dataset array (not just per-sample hashes), generation code version, generation parameters, representation format, and — critically — an explicit `audit_tier: instance | procedure` field.

**Direct answers to your sub-questions:**

- Exhaustive hashing is more than sufficient for exact duplicates — the gap was never the method.
- Yes, hash the model-consumed representation, unambiguously.
- Regenerated vs. historical: don't try to paper over this. Two tiers, reported separately. Going forward, fix it at the root — persist a content hash (ideally the array itself) at generation time, so this stops being retrospectively unrecoverable.
- When the original dataset is unavailable (true of essentially everything run so far, given unseedable generation): only the procedure-tier claim is available, and it should be backed **analytically**, not empirically — a birthday-bound calculation using the generator's entropy and the achieved sample count is actually a *stronger*, cleaner argument than re-running a regenerated stand-in and reporting its clean result as if it spoke to history. I'd make this the primary procedure-tier method, with empirical regeneration as a secondary sanity check, not the other way around as it is now.
- Yes, D1 should produce a certificate. It currently produces none.

## B. Near Duplicates / Correlated Samples — redesigned

**The core problem with the current design isn't the sample size, it's the choice of test.** A fixed threshold of Hamming distance ≤ 1 over 64-bit vectors is close to scientifically vacuous on its own: under a true independent-uniform null, the expected count of such pairs even among the full 10M-sample population is astronomically close to zero. So "0 found" is nearly guaranteed by the null itself and tells you almost nothing. **What's actually valuable is already being collected and thrown away**: the full `distance_distribution` in the D2 certificate. That distribution, tested against its theoretical shape, is a real, informative, and currently unused test.

**Redesign**: replace the fixed-threshold count with a **goodness-of-fit test** — compare the empirical Hamming-distance distribution against the theoretical Binomial(64, 0.5) distribution a well-diffused cipher should produce under independent draws.

**1. Threat**: samples that aren't byte-identical but are similar enough to functionally correlate — or, more usefully here, a distance distribution shaped in a way that reveals clustering/non-independence in generation.
**2. Claim**: "the empirical pairwise Hamming-distance distribution, within the checked subset, is consistent with the theoretical distribution expected under independent draws from a well-diffused cipher."
**3–4. H0/H1**: H0: empirical distribution = Binomial(64, 0.5). H1: meaningful deviation.
**5–6. Treatment/Control**: the "control" here is the theoretical null distribution itself, not an empirical control arm.
**7. Held constant**: representation, distance metric, pre-specified bin structure — *not chosen post-hoc after seeing the shape.*
**8. DV**: distance-distribution shape / deviation statistic.
**9. Statistical unit**: this needs care — the truly independent unit is the **sample**, not the pair. Pairwise comparisons among a fixed subset of *m* samples produce C(m,2) pairs, but those pairs are not independent of each other (many share a point), so a chi-square goodness-of-fit test's sample-size input should be reasoned about relative to *m*, not the pair count, even though the pair count is what's tabulated.
**10. Statistical method**: chi-square (or a Cramér's V–style) goodness-of-fit test against Binomial(64, 0.5), using a bin structure fixed in advance.
**11. Effect size**: total variation distance or Cramér's V between empirical and theoretical distributions — report this alongside, not instead of, the p-value, precisely because raw significance is uninformative at this scale in the wrong direction here too (a huge pair count could flag a trivially small, meaningless deviation as "significant").
**12. CI**: bootstrap CI on the TVD statistic.
**13. Decision rule**: TVD below a pre-specified practical-equivalence bound → pass. Separately: **any** near-duplicate pair at distance ≤ 1 or ≤ 2 specifically, however rare the count, warrants manual inspection rather than routine dismissal, precisely because the null predicts it should essentially never happen.
**14. Establishes**: within the checked subset, whether the near-duplicate structure matches independent-uniform generation.
**15. Does NOT establish**: full-population absence outside the subset; and — this is the more important gap — does not establish absence of **generation-level** correlation (shared key/plaintext material) that a good cipher's diffusion would hide from Hamming distance entirely. This is worth stating plainly: a Hamming-distance check on *ciphertext* is really more of a sanity check on the generation code's diffusion behavior than a genuine dataset-leakage check — its passing is close to tautologically expected for a correctly implemented cipher, and its *failure* would be the far more interesting, higher-value finding (evidence of a generation bug). The real leakage risk for cryptographic data lives one level up, at generation-parameter structure — covered under C.
**16. Type**: diagnostic + inferential, once reframed this way (properly inferential, unlike the current fixed-count approach).
**17. Certificate**: yes.
**18. Provenance**: subset-selection method and seed (this *can* be seeded — subsampling from an already-generated array is a framework-side operation, distinct from the underlying unseedable cryptographic generation, same distinction established for CE3's probe-side randomness), bin structure, distance metric.

**Principled sample size, not a round number**: run a power analysis for the chi-square test — what *m* gives, say, 80% power to detect a Cramér's V of 0.05 (a conventionally small effect) at the chosen bin resolution — and document that number as the justification for *m*, rather than 1000 chosen without a stated reason.

## C. Partition Integrity — redesigned

Exact overlap (already handled well by D1/D2's exhaustive hash-intersection) is necessary but not sufficient. Add:

- **Cross-partition near-duplicate checking**, specifically — worth explicitly verifying this is actually being run train-vs-validation and not only within-train, since that's the more serious leakage direction and I couldn't confirm from the certificate schema alone which pairs were actually compared.
- **Generation-level independence**: verify no shared RNG state or cached generation object is reused across the calls that produce train vs. validation partitions. This is exactly the class of check already done ad hoc during CE3/CE4's debugging (tracing adapter mutable state, confirming `_last_bundle` isn't reused) — it should become a **formal, named Partition Integrity check**, not something rediscovered informally each time a new stage is built.
- **Structural relation independent of Hamming distance**: shared key or plaintext material across partitions, which a good cipher's diffusion would hide from any ciphertext-level distance metric entirely — this is a generation-parameter check, not a representation-level check, and belongs here rather than under B.

## D. Distributional Integrity — the most important redesign

Your instinct not to reflexively demand significance is exactly right, and I want to be precise about why the naive fix would make things worse, not better. At N=10,000,000, a standard significance test's power grows with sample size — a class-balance difference of 0.000114, the actual number in your current D3 certificate, would produce a vanishingly small p-value under an ordinary two-sided test despite being scientifically meaningless. Bolting a chi-square test onto D3 as currently framed would manufacture false alarms, and a reviewer who understands this would read that as evidence the framework doesn't understand its own statistics — worse than D3's current silence.

**The correct tool is equivalence testing (TOST — Two One-Sided Tests), not significance testing.**

**1. Threat**: a distributional artifact (class imbalance, per-bit marginal bias, train/validation distributional drift) that could account for measured performance independent of genuine cryptographic learning.
**2. Claim**: "the observed distribution is practically equivalent to the theoretically expected distribution, within a pre-specified negligibility bound δ."
**3–4. H0/H1 (inverted from a standard test, which is the whole point of TOST)**: H0: `|difference| ≥ δ` (not equivalent). H1: `|difference| < δ` (practically equivalent). δ is fixed *before* looking at data, grounded in domain reasoning — e.g., a class imbalance large enough to meaningfully shift what "chance accuracy" means for a distinguisher, not a round number.
**5–7. Treatment/Control/Held constant**: N/A in the treatment sense — comparison is against a stated theoretical or cross-partition reference.
**8. DV**: class balance, per-bit marginal rate, feature mean/variance/entropy — same quantities D3 already computes, now with a decision procedure attached.
**9. Statistical unit**: the sample (each row independently contributes to the estimated proportion/mean).
**10. Statistical method**: TOST via two one-sided z-tests (or exact binomial equivalents at this scale) against δ.
**11. Effect size**: standardized difference (Cohen's h for proportions) — report this, not just the raw TOST verdict, since it's the quantity a reviewer will actually want to see.
**12. CI**: standard CI on the proportion/mean difference, checked against the ±δ equivalence band directly — this is visually and procedurally cleaner than a bare p-value.
**13. Decision rule**: CI fully within [−δ, +δ] → equivalence supported; CI overlapping the boundary → inconclusive; CI outside → non-equivalence, investigate.
**14. Establishes**: the tested distributional property is close enough to expected to be practically ruled out as a confound, at the chosen δ.
**15. Does NOT establish**: exact equality (nothing does); does not cover distributional properties not explicitly tested.
**16. Type**: properly inferential and confirmatory, unlike the current purely descriptive form.
**17. Certificate**: yes.
**18. Provenance**: pre-registered δ and its justification, theoretical reference used, whether comparison is against a theoretical null or the other partition.

**Which comparisons actually matter**, in priority order: (1) class balance of the actual training *label*, since it directly affects what "chance" means for every downstream accuracy claim — the single highest-value test in this whole dimension; (2) per-bit marginal rate against 0.5, which is the correct null *given* the cipher's diffusion property (an adapter-supplied assumption, not a framework default — see K); (3) train-vs-validation equivalence directly against each other, which matters more than either partition's absolute distribution for the "could a distributional artifact explain generalization" question specifically.

**Multiple-comparisons note specific to this section**: if the per-bit marginal test is run individually across all 64 bits as 64 separate confirmatory decisions, *that* specific family needs correction (Benjamini-Hochberg FDR is more appropriate than Bonferroni here, since these are structurally repeated, similar tests) — full treatment under J.

## E. Label / Metadata / Feature / Generation-Order / RNG Leakage

Sorting these by where they actually belong:

**Belongs in Dataset Integrity, currently absent, worth adding:**

- **Label leakage / generation-order artifact check**: does sample index or generation batch correlate with the label (a classic bug — e.g., positive samples generated before negative ones, pre-shuffle)? Cheap, high-value, currently nowhere in the codebase. Test: correlation between sample index and label; if any batching/ordering metadata is recorded, a weak classifier restricted to *only* that metadata should not predict the label above chance — a "canary" probe, distinct in purpose from D4's full label-shuffle.
- **Univariate feature-label leakage screen**: cheap check that no single feature is a near-deterministic function of the label — for Gohr's raw-bit representation this should trivially pass by construction, but it's a generic, near-free diagnostic worth having for any future adapter where it isn't trivial.
- **RNG structural artifact check**: forward-looking — currently low-risk given `os.urandom()`, but becomes a real concern if the pipeline ever migrates to a seeded PRNG for reproducibility (a live tension surfaced earlier in this project). Worth having the check exist now rather than retrofitting it under pressure later.

**Belongs in the generic interface, but a no-op for this specific adapter:**

- Metadata leakage, filename/path artifacts, train/test preprocessing-fit differences — none apply to Gohr's raw-bit, metadata-free, unnormalized representation, but a generic framework claiming reusability needs the interface to *require* an adapter to address them, even if this adapter's answer is "not applicable." Silently omitting the interface slot would be exactly the kind of Gohr-specific coupling Section K is trying to prevent.

## F. Controlled Perturbations — D4 critique and additions

**What D4 actually establishes, precisely**: that the training *pipeline* does not produce above-chance accuracy when the label carries no information — this is a real, valid, well-understood permutation-test-style null-model check, not a weak one. I don't want to overstate a weakness that isn't there.

**What it does not establish, and what remains open**: label-shuffle is a blunt instrument — it destroys genuine cryptographic signal *and* any potential artifact simultaneously, so a clean near-chance result under shuffle is consistent both with "no leakage exists" and with "leakage exists but was symmetric and got diluted along with the real signal." It tests "does *some* exploitable association exist" in a pooled sense; it does not test specific, targeted bug patterns like generation-order leakage precisely — that's exactly why E's targeted screen is a necessary complement, not a duplicate.

**One thing worth verifying before trusting the existing D4 result, not assuming**: does the current shuffle implementation touch *only* the label-to-feature pairing, leaving feature order, partition structure, and everything else byte-for-byte identical? I haven't re-read `perturbations/lable_shuffle.py` in this pass — this is a "verify, don't assume" item for the actual redesign work.

**Additional perturbations worth adding:**

- **Partition-swap perturbation**: train on what was validation, validate on what was train — should produce statistically equivalent performance if partitions are genuinely exchangeable. Tests partition-level integrity directly, complementary to D4's label-level test.
- **Feature-shuffle-within-sample perturbation** (a file already exists for this — worth checking what it currently does): consistently permute *which bit position is which* across all samples, destroying cryptographically meaningful structure while preserving every marginal statistic. This is conceptually the dataset-side analogue of CE4's structural-vs-control intervention design — a nice, defensible internal consistency across the framework worth calling out explicitly in the paper.
- **Positive-control calibration check**: deliberately inject a *known*, specific-magnitude class imbalance and verify D3's redesigned TOST actually flags it at the expected magnitude. This is the single most valuable addition in this whole section, because it directly answers the distinction you raised yourself: "finding no evidence of a problem" only means something if the test has been shown to have power to find a problem when one genuinely exists. Without this, D3 passing is uninterpretable; with it, it's calibrated.

## G. Dataset Size / Sampling — what D6 should actually be

Not inferred from the directory names alone. The most scientifically valuable role available for this slot: **training-set-size sensitivity / sample-efficiency analysis** — does distinguisher performance plateau well below the full \~10M-sample budget? This has a specific, useful function *within* Dataset Integrity: if performance is already saturated at a fraction of the data, then the near-duplicate and duplication concerns from A/B become *even less able* to explain the model's accuracy, because there's enough headroom that modest contamination couldn't plausibly be the primary driver. That's a genuine, non-trivial connection between D6 and the rest of the dimension, worth stating explicitly rather than leaving D6 as an orphaned artifact set.

**Classification**: optional/diagnostic, not confirmatory — it strengthens the overall dataset-integrity story but doesn't directly rule out a specific named threat the way A–F do.

## J. Multiple Testing

Split into **diagnostic** (exploratory, individually reported, no correction needed — per-bit marginal table, distance-distribution plot) versus **confirmatory** (feeds an overall Dataset Integrity verdict — exact-duplicate census, redesigned near-duplicate goodness-of-fit, redesigned D3 TOST, D4 shuffle, E's leakage screens).

**Within** the confirmatory family, don't apply a blanket correction across everything — these test *different* threats, not repeated looks at the same hypothesis, and Bonferroni across genuinely distinct threat categories is both overly conservative and conceptually the wrong tool (same reasoning already applied to CE3's two-test family at α=0.025). Correct **within** genuinely repeated sub-families instead — the clearest case is the 64 per-bit marginal comparisons under D3, which are structurally identical repeated tests and should get Benjamini-Hochberg FDR control, not Bonferroni (FDR is the better choice here given the number of tests and the exploratory-adjacent nature of per-bit reporting).

**Aggregate verdict**: if you want one overall Dataset Integrity PASS/FAIL, make it conjunctive — all confirmatory tests must pass — rather than a softer majority rule. Conjunctive is more conservative and considerably easier to defend to a skeptical reviewer.

## K. Architecture — generic vs. adapter-specific

**Generic framework owns**: certificate schema, exact-hash census machinery (given an array + a representation-extraction function), goodness-of-fit/TOST procedures (given a data array + a theoretical null specification supplied externally), the shuffle-and-retrain harness (given a training function), coverage-bound calculation, the diagnostic/confirmatory classification machinery, decision-vocabulary enforcement (exhaustive vs. inferential).

**Adapter owns**: what counts as "the model-consumed representation" (Gohr: 64-bit binary encoding); the theoretical null model for near-duplicate and marginal-frequency tests (Gohr: independent-uniform, justified *by* the cipher's diffusion property — this is a cryptographic assumption the generic framework cannot supply on its own for an arbitrary dataset); what constitutes generation-level structure worth checking (Gohr: key/plaintext reuse — the framework doesn't know what a "key" is, only the adapter does); the training/retraining hook for D4's shuffle test.
